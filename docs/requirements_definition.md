# 要件定義書

## 1. プロジェクト概要

### 1.1 目的
特定のWebサービス（shinchakun.net）における「スケジュール設定」と「待機接客配信」の操作を約200アカウント分完全自動化し、業務効率化とヒューマンエラー防止を実現する。

### 1.2 対象サービス
- サービス名: shinchakun.net
- クラウド版ログインURL:
  - https://doors1.shinchakun.info/dokodemo/#/
  - https://doors2.shinchakun.info/dokodemo/#/
- 自動判別機能: どちらのURLが有効かを自動判別し、アカウントごとに記録

## 2. 機能要件

### 2.1 スケジュール自動更新機能

#### 2.1.1 実行スケジュール
- **実行時間帯**: 毎日AM7:00〜10:00
- **実行頻度**: 1日1回

#### 2.1.2 処理内容
1. 週間スケジュールを確認
2. 週間スケジュールに一つでも「出勤設定」があるキャストを特定
3. 該当キャスト全員の翌日の設定を「出勤設定」に変更
4. 変更内容を登録

#### 2.1.3 対象アカウント
- 全アカウント（約200アカウント）
- アカウントごとに独立して処理

### 2.2 待機接客配信の自動設定機能

#### 2.2.1 実行スケジュール
- **実行間隔**: 60分〜90分（ランダム）
- **実行頻度**: 継続的に実行

#### 2.2.2 処理内容
1. 出勤キャスト数を確認
2. 人数制限チェック（3人以下で停止）
3. 時間制限チェック（退勤時刻の10分前を超えない）
4. ステータス制御（「接客中」→「非更新エリア」入場時、「待機中」に変更）
5. 待機接客配信の設定を更新

#### 2.2.3 制約条件
- **人数制限**: 出勤キャストが3人以下になった場合、設定を停止
- **時間制限**: 設定時間が退勤時刻の10分前を超えないように調整
- **ステータス制御**: 「接客中」のキャストが「非更新エリア」に入った際、「待機中」に即座に変更

### 2.3 セッション競合回避機能

#### 2.3.1 要件
- 同一アカウントでの手動操作と自動更新が競合しないようにする
- ログアウトを防止する

#### 2.3.2 実装方針
1. **手動操作検知**
   - Session Tokenの変化を検知
   - DOM操作の同時発火を検知
   - 「手動操作フラグ」を即時設定

2. **自動スキップ**
   - 手動操作が検知されたアカウントのみ処理をスキップ
   - 他アカウントへの影響はゼロ

3. **並列処理キュー**
   - アカウントごとに独立した処理キュー
   - スキップ時も他アカウントは継続実行

4. **ログ記録**
   - どのアカウントが手動操作により除外されたかを記録
   - 後から確認可能

### 2.4 アプリ停止検知と再起動機能

#### 2.4.1 要件
- 画面に「赤い×」（アプリ停止）が表示された際、自動でアプリケーションを再起動

#### 2.4.2 実装方針
1. 定期的に画面を監視
2. 「赤い×」要素を検知
3. ブラウザセッションを再起動
4. ログイン状態を復元
5. 処理を再開

### 2.5 エラー通知機能

#### 2.5.1 要件
- エラー発生時、指定のGoogleアカウントのChromeブラウザにエラーログをポップアップ通知

#### 2.5.2 実装方針
- Chrome拡張機能を利用
- WebSocketまたはHTTP経由で通知
- エラーレベルに応じた通知優先度

### 2.6 管理機能

#### 2.6.1 Web管理画面
- ID、パスワード、店名の管理
- アカウント一覧表示
- アカウント追加・編集・削除
- 各機能のON/OFF切り替え
- ログ閲覧
- 稼働状況の監視
- エラー一覧表示
- 手動操作検知の履歴

- 200アカウントの処理を安定して実行

### 3.2 信頼性
- エラーハンドリングの徹底
- 自動復旧機能
- ログの詳細記録

### 3.3 保守性
- 実行するだけで修正できる修正パッチ機能
- エラー修正マニュアルの提供
- コードの可読性と拡張性

- セッション管理の安全性
